# Lecture 3: Branching, Merging, & Collaboration

---

## The Killer Feature of Git: Branching

Branching is the single most powerful feature of Git.

**Branches in Git are cheap and fast.**

This encourages a workflow where you create a branch for *everything*:
- A new feature
- A bug fix
- An experiment
- Even a tiny change

This isolates work, preventing you from destabilizing your main `main` branch. It enables **fearless experimentation**.

---

## Visualizing Branching

1.  Your history starts on `main`.
    ```
    A---B---C (main)
    ```
2.  You create a new branch called `feat/login`. It points to the same commit as `main`.
    ```
    A---B---C (main) (feat/login)
    ```
3.  You make a commit on the `feat/login` branch. The `feat/login` branch moves forward, while `main` stays put.
    ```
          D (feat/login)
         /
    A---B---C (main)
    ```
4.  You add another commit to your feature branch.
    ```
          D---E (feat/login)
         /
    A---B---C (main)
    ```
---

## Merging: Bringing Work Together

Merging unites two branches. Let's say work has continued on `main` while you were on your feature branch.

```
      D---E (feat/login)
     /
A---B---C---F (main)
```

To merge `feat/login` into `main`:
1.  `git switch main`
2.  `git merge feat/login`

---

## Visualizing a Merge Commit

Git performs a "three-way merge" and creates a new **merge commit**.

- It looks at three snapshots:
    1. The common ancestor (`B`)
    2. The tip of `main` (`F`)
    3. The tip of `feat/login` (`E`)
- It combines the work and creates a new commit `G` that has **two parents**.

```
      D---E
     /     
A---B---C---F---G (main)
```
The merge commit `G` represents the integration of the feature.

## Remotes: Working with Others

So far, everything has been **local**. To collaborate, we need a **remote** repository—a shared source of truth. This is what GitHub provides.

- A `remote` is a pointer to another repository.
- The default name for the remote you clone from is `origin`.

```
+----------------+      git push     +----------------+
|                |  -------------->  |                |
|  Local Repo    |                   |  Remote Repo   |
|  (.git folder) |  <--------------  | (e.g., GitHub) |
|                |      git pull     |                |
+----------------+                   +----------------+
```

---

## `push` and `pull`

- **`git push <remote-name> <branch-name>`** (`git push origin main`)
  - Uploads your branch and all its commits to the remote.
  - This is how you share your work.

- **`git pull <remote-name> <branch-name>`** (`git pull origin main`)
  - The most common way to get updates from others.
  - It's actually two commands in one:
    1. `git fetch`: Downloads all the new commits from the remote.
    2. `git merge`: Merges the remote branch into your local branch.

---

## The GitHub Flow: A Code Review Culture

The goal is not just to merge code, but to merge *high-quality* code. This happens via **Pull Requests**. (Reference: *Software Engineering at Google*)

1.  **Push your feature branch** to the remote (`git push origin feat/login`).
2.  **Open a Pull Request (PR)** on GitHub. This is a formal proposal to merge your branch.
3.  **Describe your changes.** Explain the *why*, not just the *what*. Link to the issue it solves.
4.  **Team members review the code,** add comments, and suggest changes.
5.  **You make more commits** on your branch to address the feedback and push them up. The PR updates automatically.
6.  Once approved, the branch is **merged into `main`** via the GitHub UI.

---

## Help! Merge Conflicts!

A merge conflict happens when you and another person change the **same lines of the same file** on different branches. Git doesn't know which version is correct.

**It's not scary!** Git is just asking you, the human, to make a decision.

When a conflict happens, `git merge` will fail and Git will insert conflict markers into the file:

```
<<<<<<< HEAD
This is the version from your current branch.
=======
This is the version from the branch you are trying to merge.
>>>>>>> feat/login
```

---

## How to Resolve a Conflict

1.  **Don't Panic.** `git status` will show you which files have conflicts.
2.  **Open the conflicted file** in your editor.
3.  **Decide which code to keep.** Delete the lines you don't want, and remove the `<<<<<<<`, `=======`, `>>>>>>>` markers.
4.  The final code should be exactly what you want it to be.
5.  **Save the file.**
6.  `git add <the-resolved-file>` to tell Git you're done.
7.  `git commit` to finalize the merge.

## Collaboration Workshop

1.  Go to GitHub and create a new, public repository.
2.  **Clone** it to your machine: `git clone <your-repo-url>`.
3.  `cd` into the new directory.
4.  Create and switch to a new branch: `git switch -c my-first-feature`.
5.  Create a `README.md` file and add some text.
6.  `git add` and `git commit` your change.
7.  **Push** your branch to GitHub: `git push origin my-first-feature`.
8.  Go to your repo on GitHub. You will see a prompt to **open a Pull Request**. Do it.
9.  Review your own PR. Add a comment.
10. **Merge the Pull Request** using the GitHub UI.
11. Locally, switch back to main: `git switch main`.
12. **Pull** the changes from the remote: `git pull origin main`.
13. Your `README.md` file should now appear locally on your `main` branch!
